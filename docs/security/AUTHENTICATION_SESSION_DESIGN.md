# HanboweiOJ 身份认证与会话安全设计

版本：v0.1｜状态：Draft，待评审  
适用范围：内部 MVP；学生、教师、管理员；浏览器 Web 前端与 FastAPI API

## 1. 目标与非目标

### 目标

- 只允许管理员创建内部账号，不开放公众自助注册。
- 可靠识别用户身份，并在服务端执行角色权限和对象归属检查。
- 登录失败不泄露用户名是否存在、账户是否停用等信息。
- 会话可过期、主动撤销，并能在账户停用或凭据变更后失效。
- 认证、授权、审计和限流可测试、可追踪。

### 当前不做

- 不开放公众注册、第三方 OAuth、社交登录或长期 API Token。
- 不在浏览器 localStorage/sessionStorage 保存认证凭据。
- 不把前端隐藏按钮当作权限控制。
- 不在本阶段实现登录 HTTP 路由或生产会话。

## 2. 已有基础

当前代码已有：

- `User`：规范化唯一用户名、Argon2id 密码哈希、角色、启用状态。
- `normalize_username`：统一用户名为小写规范形式。
- `hash_password` / `verify_password`：密码哈希与验证。
- `authenticate_user`：认证服务层，成功返回启用用户，失败统一返回 `None`。

以上只是认证基础，不等于完整登录系统。HTTP 接口、会话存储、CSRF、限流、权限依然需要单独实现和验收。

## 3. 会话方案建议

### 建议：随机不透明令牌 + 服务端会话记录

对首期同源浏览器应用，优先考虑服务端会话，而不是把 JWT 当作默认方案：

1. 服务端使用密码学安全随机数生成高熵会话令牌。
2. 浏览器只通过 Cookie 保存原始令牌。
3. 数据库只保存令牌的 SHA-256 摘要，不保存可直接复用的原始令牌。
4. 每次请求由服务端查找有效会话，再读取对应用户和当前账户状态。
5. 登出、账户停用、密码重置或管理员撤销时，可立即使会话失效。

理由：首期需要可撤销、简单可审计的内部账户体系；服务端会话避免自行处理 JWT 撤销列表、过期令牌残留和密钥轮换等额外复杂度。Redis 可用于限流或缓存，但不应成为唯一会话事实来源，除非另行设计持久化和恢复策略。

### Cookie 属性建议

- `HttpOnly`：禁止前端脚本读取会话 Cookie。
- `Secure`：生产环境仅通过 HTTPS 发送。
- `SameSite=Lax`：作为默认起点；若部署形态需要跨站 Cookie，必须重新评估并强化 CSRF。
- `Path=/`；不设置不必要的 `Domain`。
- 生产环境使用明确的 Cookie 名称和合理的过期时间。
- 本地 HTTP 开发配置与生产配置分开，不允许把开发例外带入生产。

## 4. 建议的会话数据模型

建议新增 `user_sessions` 表，字段至少包括：

| 字段 | 用途 |
|---|---|
| id | UUID 主键 |
| user_id | 关联 users.id，用户删除时按策略撤销/清理 |
| token_hash | 原始会话令牌的 SHA-256 摘要，唯一且非空 |
| created_at | 创建时间 |
| expires_at | 绝对过期时间 |
| last_seen_at | 最近活动时间（更新频率需节制） |
| revoked_at | 撤销时间，可空 |
| created_ip_hash（可选） | 如确有安全审计需要，优先评估哈希或不采集 |
| user_agent_summary（可选） | 仅保存必要摘要，不保存完整敏感指纹 |

约束和索引：

- `token_hash` 唯一索引。
- `user_id` 普通索引，便于撤销该用户全部会话。
- 查询有效会话必须同时满足未撤销、未过期、用户存在且 `is_active = true`。
- 不把 IP 或 User-Agent 当作强身份凭据。
- 会话记录不得包含密码、原始令牌或其他认证秘密。

## 5. 生命周期要求

- 登录成功后创建新会话；不得复用登录前的匿名会话标识。
- 登录、权限提升或重新认证后轮换会话令牌。
- 登出时撤销当前会话，并清除浏览器 Cookie。
- 修改密码、管理员重置密码、账户停用或安全事件时，撤销该用户全部会话。
- 同时设置绝对有效期与可选空闲有效期；具体时长由内部使用场景评审确定。
- 会话过期或撤销后，API 返回统一未认证响应。
- 不在日志、错误消息、URL、分析事件中记录原始令牌。

## 6. CSRF、CORS 与请求来源

Cookie 会自动随浏览器请求发送，因此不能仅依赖 CORS 防护。

对所有改变状态的请求（POST、PUT、PATCH、DELETE）：

- 使用 CSRF Token（建议同步器 Token，或经评审的双提交方案）。
- 校验 `Origin`；必要时结合 `Referer` 作为补充。
- 对不符合预期来源的请求拒绝处理。
- GET/HEAD/OPTIONS 不得产生业务状态变更。
- 继续使用明确的 CORS allowlist；禁止通配符与凭据模式组合。
- 登录、登出和会话刷新接口也纳入来源与 CSRF 评审。

## 7. 登录限流与失败处理

- 对登录尝试按来源 IP 和规范化用户名维度限流，并设置全局保护。
- 限流策略需避免简单永久锁定单个账号，防止攻击者利用锁定机制阻断学生学习。
- 登录失败统一使用通用响应，不区分用户名不存在、密码错误或账户停用。
- 对不存在的用户名执行 dummy Argon2id 验证，以降低明显的时间差；这不能保证严格恒定时间。
- 密码验证成本较高，必须配合并发限制、请求体限制和限流，防止资源耗尽。
- 不记录明文密码、密码哈希、Cookie、CSRF Token 或原始会话令牌。
- 记录必要的安全事件元数据，但控制保留期限和访问范围。

## 8. 授权边界

认证只回答“当前用户是谁”；授权还必须回答“该用户能否对这个对象执行这个动作”。

每个受保护 API 都必须在服务端检查：

- 用户会话有效且账户启用。
- 角色是否允许该操作。
- 对象归属是否满足规则，例如学生只能读取本人提交，教师只能管理获授权班级。
- 管理员操作是否需要额外确认或审计。

角色建议：

- 学生：本人提交、学习进度和已授权课程。
- 教师：本人负责或被授权班级及其教学数据。
- 管理员：内部账号、角色、内容与系统管理。

不能仅依赖前端路由、按钮显示或客户端传入的角色字段。

## 9. 建议 API 边界

后续实现可考虑：

- `POST /api/v1/auth/login`：校验凭据并建立会话。
- `POST /api/v1/auth/logout`：撤销当前会话。
- `GET /api/v1/auth/me`：返回当前用户的最小公开资料与角色。
- `GET /api/v1/auth/csrf`：按选定 CSRF 方案提供 Token。
- 管理员专用账号创建、停用、重置凭据接口应放在独立管理权限边界中。

这些是建议接口，不代表当前仓库已经实现。响应中不返回密码哈希、会话令牌摘要或内部安全字段。

## 10. 测试验收清单

### 认证

- 正确凭据可以认证；错误密码、未知用户、停用用户返回一致失败。
- 用户名大小写归一化后行为一致。
- 畸形输入和畸形哈希安全失败。
- 不泄露用户是否存在。

### 会话

- 登录创建新会话；数据库仅保存令牌摘要。
- 令牌随机且不可预测；会话过期和撤销立即生效。
- 登出只撤销当前会话。
- 密码变更、账户停用可撤销全部会话。
- Cookie 属性符合部署环境。

### CSRF 与授权

- 缺失或错误 CSRF Token 的状态变更请求被拒绝。
- 非允许来源请求被拒绝。
- 学生不能访问他人提交；教师不能访问未授权班级。
- 修改客户端传入的 user_id、role 或对象 ID 不能绕过服务端授权。

### 运维与隐私

- 登录限流有效，且不会轻易造成账号永久锁定。
- 日志不含密码、哈希、Cookie、CSRF Token 或原始令牌。
- 审计日志最小化收集，并有访问控制和保留策略。

## 11. 实施顺序建议

1. 评审并确认会话方案、有效期和部署拓扑。
2. 增加会话模型与 Alembic 迁移，并覆盖撤销/过期测试。
3. 实现 Cookie、CSRF、来源校验与限流组件。
4. 实现登录、登出、当前用户接口。
5. 实现角色与对象级授权依赖。
6. 完成越权、CSRF、会话撤销和限流测试后，才允许内部试用。

在上述验收完成前，不应将认证功能暴露给真实学生账户或公网用户。
